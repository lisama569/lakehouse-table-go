# lakehouse-table-go

基于本地文件系统的快照式表格读写层：用本地目录模拟数据文件与表元数据，
保证跨进程/跨实例并发写入、失败重试、带数据列改名与结构演进之后的数据结论
一致且可解释，并向下游输出可断点续读的行级变更明细。

## 存储布局

```
<root>/<table>/
├── meta/
│   ├── HEAD                    # 当前快照 ID（原子替换写入）
│   ├── LOCK                    # 表级跨进程排他锁文件（flock）
│   ├── snapshots/<id>.json     # 快照元数据（不可变）
│   ├── snapshots/<id>.changes.json # 快照行级变更流水（不可变）
│   └── batches/<batchID>       # 已提交批次标记（幂等依据）
└── data/<file>.json            # 快照数据文件（不可变）
```

## 提交与快照语义

- **快照为单位提交**：`Commit(expectParent, batch)` 把一批变更（upsert/delete）
  合并为一个新快照。提交过程先写数据文件、行级变更流水与快照元数据，
  最后 CAS 推进 `HEAD`；读取只触碰 `HEAD` 或历史快照，因此**任何时刻都看不到
  部分生效的中间状态**。
- **跨进程 / 跨实例乐观并发控制**：提交在进程内互斥锁之外，还通过
  `meta/LOCK` 上的 `flock(2)` 排他锁跨进程串行化。多个服务实例、独立脚本或
  命令行工具同时打开同一张表、基于同一份最新 `HEAD` 提交时，恰好一个提交
  生效，其余在锁内重读 `HEAD` 后明确收到 `ErrCommitConflict`。
  调用方据此与"数据/结构有问题"的错误区分：冲突类**直接用新 `HEAD` 重试即可**，
  而 `ErrInvalidChange`、`ErrSchemaIncompatible` 必须回去改数据/结构，重试无用。
  冲突方基于最新进展重试时，配合确定性合并与批次幂等，**不会产生重复行、
  不会丢更新，也不会覆盖已成功提交的那份数据**。
- **可区分的失败原因**（均可用 `errors.Is` 判定）：
  | 错误 | 含义 | 调用方动作 |
  |---|---|---|
  | `ErrCommitConflict` | 父快照已过期（并发冲突，含跨进程/跨实例） | 用最新 `HEAD` **重试** |
  | `ErrDuplicateBatch` | 同一 `BatchID` 已提交（幂等重放，数据不变） | 视为成功，无需重试 |
  | `ErrSchemaIncompatible` | 结构演进/列改名不兼容 | 修改结构，重试无用 |
  | `ErrInvalidChange` | 变更内容非法（缺主键、类型不符等） | 修改数据，重试无用 |
  | `ErrTableNotFound` / `ErrTableExists` | 表不存在 / 已存在（创建亦跨进程互斥） | 对应处理 |
- **幂等与重试**：每个批次携带唯一 `BatchID`。已提交的批次重放时返回
  `ErrDuplicateBatch` 且不改动数据——失败重试不会产生重复行或丢失更新，
  重放前后行数与校验和一致（测试中以 FNV 校验和验证）。
- **确定性合并规则**：行按主键标识；upsert 覆盖同主键整行，delete 删除；
  同批次同主键多次出现时后者覆盖前者；upsert 缺失列按结构缺省值补齐；
  快照内行按主键排序，读取结果可复现。
- **增量读取（快照流水）**：`ReadSince(seq)` 返回序号大于 `seq` 的快照流水
  （含快照 ID、父快照、批次 ID）。
- **增量消费（行级变更明细）**：`ReadChangesSince(seq)` 在快照推进信息之外，
  还返回该快照内真实发生的行级变更 `RowChange`：

  | 字段 | 含义 |
  |---|---|
  | `Seq` / `Order` | 所属快照序号 / 快照内发生顺序 |
  | `Kind` | `insert`（新增）/ `update`（更新）/ `delete`（删除墓碑） |
  | `PK` | 变更涉及的主键值 |
  | `Row` | 变更后的整行列值；`delete` 事件只带主键（`Row` 为空） |

  规则与保证：
  - 顺序即变更在批次中的出现顺序；同一主键在同一批次内连续变更会产生多条事件；
  - 同值 upsert、删除不存在的行不产生事件（流水只包含真正改变状态的变更）；
  - 明细与对应快照数据严格一致，可重放审计；
  - 流水随快照不可变地持久化，**同一次读取重复执行结果一致**；
  - 以最后一个快照的 `Seq` 作为断点**续读**，只返回尚未消费的部分。

## 结构兼容规则

### 带数据的列改名：`RenameColumn(from, to)`

用于"把某一列改名后继续沿用"的场景，是与普通结构演进不同的显式迁移：

- **数据原样搬运**：逐行把旧列名的值写到新列名，列类型、顺序与缺省值保留，
  同一行其他列（含主键）完全不受影响；迁移前后按主键读出的数据对得上。
- **旧快照不回归**：迁移只生成一个新快照；改名之前的历史快照仍携带当时的
  结构，按旧列名读到的就是当时的值，稳定且可复现。
- **快照带改名标记**：迁移快照的 `rename = {from, to}` 记录本次改名，便于审计。
- **明确拒绝的不兼容改动**（返回 `ErrSchemaIncompatible`）：
  - 改主键列的名字；
  - 源列不存在、目标列名与既有列冲突、新旧列名相同。
- 改名之后按新结构正常读写；之后再做普通结构演进（如新增列）也不受影响。

### 普通结构演进：`EvolveSchema(newSchema)`

生成一个新快照，数据按新结构重写：

- **新增列**：允许。旧数据该行填列的 `Default` 值（未设置则为 NULL）。
- **删除列**：允许。该列数据被丢弃，读取方不会看到错位或串列的数据。
- **重命名列（不保留数据）**：经 `EvolveSchema` 表达时仍视为"删除旧列 +
  新增新列"，新列按缺省值填充；**需要保留历史值请改用 `RenameColumn`**。
- **不允许**：修改主键、修改保留列的类型（返回 `ErrSchemaIncompatible`）。
- **旧快照可读**：历史快照各自携带当时的结构，结构变更后读取旧快照
  结果不变且可复现。

## 本地验证

```bash
go build ./...              # 编译
go test ./table/ -v         # 运行测试，日志打印快照标识与变更流水
go test ./... -race         # 竞态检测
go test ./... -count=10     # 多轮重复，验证并发用例稳定可复现
```

> 跨进程用例会现场 `go test -c` 编译测试二进制，再启动多个真实 OS 进程
> （worker）同时打开同一张表提交，因此运行环境需要可用的 Go 工具链。

测试覆盖：

- `TestCrossProcessConcurrentCommit`：6 个独立 OS 进程基于同一 `HEAD` 并发提交，
  恰好 1 个成功、5 个收到 `ErrCommitConflict`；冲突进程基于最新 `HEAD` 循环重试
  （成功者重放自己的批次收到 `ErrDuplicateBatch`），最终无重复行、无丢更新、
  成功提交未被覆盖，并打印完整快照流水；
- `TestMultipleHandlesInProcess`：同一进程内多个独立句柄（模拟同机多实例），
  同样恰好一个成功、其余可区分失败、重试后数据完整；
- `TestDistinguishableRejection`：冲突（可重试）与缺主键/类型不符
  （`ErrInvalidChange`，需改数据）原因互不混淆；
- `TestRenameColumn`：`name -> display_name` 后新列名读到历史值、其他列不变、
  按主键新旧快照对得上；旧快照按旧结构与值稳定复现；改名后可继续写入并再演进；
  动主键 / 源列缺失 / 目标冲突 / 同名 / 改类型均被明确拒绝；
- `TestChangeFeed`：insert/update/delete 明细完整（删除为只带主键的墓碑）、
  顺序稳定、无变化变更被过滤、重复读取一致、断点续读只返回未消费部分；
- `TestConcurrentCommitConflict`：8 个写入者并发提交同一父快照，
  恰好 1 个成功、7 个收到 `ErrCommitConflict`，冲突者重试后全部落库；
- `TestIdempotentReplay`：同一批次重放返回 `ErrDuplicateBatch`，
  行数与校验和保持不变；
- `TestSchemaEvolution`：新增列缺省值、删除/重命名列不串列、
  旧快照可复现读取、不兼容演进被拒绝；
- `TestReadSince`：增量读取返回完整快照流水。
